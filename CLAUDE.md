# LogiBTP

- Contexte : liens entre modules dans [MODULES.md](MODULES.md) ; contexte condensé de chaque partie dans son `CLAUDE.md` (`socle/`, `modules/<nom>/`, `client/`, `src/`, `db/`), chargé quand on travaille dans le dossier.
- Dépendances externes par module (npm, NuGet, polices) : [DEPENDANCES.md](documentation/DEPENDANCES.md), généré par `npm run rapport-dependances` à relancer après tout ajout ou mise à jour.
- Tâches à faire et décisions reportées : [TACHES.md](documentation/TACHES.md) (à mettre à jour quand une tâche est faite ou reportée).

- Répondre et documenter en français ; code, commentaires et noms en français (sauf API techniques).
- Architecture : `socle/` (sans métier) → `modules/<nom>/` (classes mères, méthode patron) → cœur (`src/`, `client/`, `db/`) qui spécialise. Un module ne dépend jamais du cœur ; le module Métré ne dépend pas du module Document.
- Moteurs miroirs JS / C# : `MoteurDocument` (`modules/document/js/src/moteur-document.js`, `modules/document/dotnet/LogiBTP.Documents/Calcul/MoteurDocument.cs`) et `MoteurDevisBtp` (`client/src/calcul/moteur-btp.js`, `src/LogiBTP.Calcul/MoteurDevisBtp.cs`). Toute règle modifiée l'est dans les deux, avec un cas dans les jeux du module ou du cœur, puis `npm test`, `npm run exporter-resultats` et `dotnet test LogiBTP.slnx`.
- Jamais de `Number` pour un montant côté JS (decimal.js) ; une seule fonction d'arrondi par moteur (demi vers l'infini).
- Noms de colonnes du DDL partout (snake_case préfixé) ; les propriétés C# en PascalCase s'y mappent automatiquement. Colonnes génériques (`modules/document/js/src/types.js`) et BTP (`client/src/calcul/colonnes-btp.js`) alignées sur les entités (des tests le vérifient).
- Schéma géré par les scripts SQL de chaque module (`modules/*/db`) puis du cœur (`db/`), pas de migrations EF ; les colonnes métier s'ajoutent par `ALTER TABLE` dans le cœur.
- Module Liste : la sémantique des requêtes (recherche, segments, tri, curseur, colonnes multivaluées `ARRAY`) est répliquée entre `modules/liste/js/src/requete.js` et `ConstructeurRequete.cs` (jeux `modules/liste/tests/cas`) ; toute requête de données s'exécute en lecture seule. Les vues par défaut se modifient dans `client/src/app/vues-liste.js`, puis `npm run generer-vues-liste --workspace client`.
- Module Fiche : validation des champs répliquée entre `modules/fiche/js/src/validation.js` et `ValidationFiche.cs` (jeu `modules/fiche/tests/cas` ; `erreurRequete` ↔ `ErreurRequete` pour les listes par requête SQL) ; paramétrage : RGPD des champs du logiciel (`pcf_confidentiel`), champs supplémentaires par onglet / groupe / ordre, liste de valeurs par SELECT (lecture seule, côté serveur), type mot de passe chiffré (`POST /{id}/secret`, journalisé) ; types de fiches dans `client/src/app/fiches/definitions.js` (puis `npm run generer-vues-liste --workspace client`) ; les règles métier des fiches du cœur existent en JS (`fiches.js`) et en C# (`SpecialisationFicheBtp`). Champs supplémentaires : colonne JSONB par table. Champs gérés (`gere: true`, sans colonne) : lus et écrits par `SpecialisationFiche.LireGeresAsync / ValiderGeresAsync / EcrireGeresAsync` (mémoire : `types.<type>.geres`).
- Module GED : chaîne du coffre-fort répliquée entre `modules/ged/js/src/coffre.js` et `ChaineCoffre.cs` (texte d'entrée, horodatage à la milliseconde UTC, jeu `01_coffre.json`), conservation des versions entre `versions.js` et `RegleVersions.cs` (jeu `02_versions.json`) ; `FournisseurGedMemoire` applique les mêmes règles que `ServiceGed`. Le journal et les documents du coffre sont protégés par des triggers (`db/050`) : ne jamais les contourner. Organisation et cycle de vie (`db/051`, rejouable) : répertoires, confidentialité et accès (`acces.js` ↔ `AccesGed.cs`, jeu `06_acces.json`), texte extrait et plein texte, dérivations, rétention (`retention.js` ↔ `RegleRetention.cs`, jeu `04` ; règles paramétrées dans `/parametres/ged`, archivage automatique chaque nuit et par base : `ArchivageGed`, section `Ged:Archivage`), classification automatique (`classification.js` ↔ `ClassificationGed.cs`, jeu `05`), archive séparée (jamais pour le coffre : archivage sur place). Explorateur : arborescence du cœur `ArborescenceBtp` (`client/src/app/ged/arborescence.js` : Projet › Affaire › Chantier › Marché › famille (Ventes, Achats, Stock) › type de document › documents, dossiers virtuels pour la famille et le type ; liens symboliques vers les documents enfants dans un regroupement, enfants imbriqués depuis un document) ; un dépôt dans un dossier lie la pièce à l'élément du dossier.
- Client : application web à routes (`client/src/app/pages`, déclarées dans `pages/index.js`) ; une page dérive de `PageBase` (`ouvrir`, titre, `modifiee`, `quitter`, `reprendre`, `masquer`, `fermer`, `urlCourante` ; `liberer` n'existe que dans les pages document et fiche) et toute ouverture d'écran passe par `app.naviguer(url, { nouvelleFenetre })`, jamais par un panneau superposé ; fermer une fiche ou un document passe par `app.fermerPage(defaut)` (fenêtre séparée : la fenêtre se ferme, sinon retour). Menus du bandeau et raccourcis : `client/src/app/navigation/menus.js` ; widgets : `navigation/widgets.js`.
- Une base par société (sous-domaine) : les contextes EF prennent la connexion de `SocieteCourante` par requête ; tout cache singleton dépendant du schéma est indexé par base ; ce qui est propre à une société hors de la base (documents de la GED) est rangé sous le nom de sa base (`SocieteCourante.Base`).
- Postes de pied : groupes « Postes de pied HT / TTC » toujours affichés (vides : lignes d'accueil, `EditeurDocument.insererPoste`) ; type d'élément `POSTE_PIED` de la bibliothèque (`modules/bibliotheque/db/063`, fiche élément : groupe Poste de pied ; démo RG5, PRORATA, REMISE5, FRAISDOS) inséré dans le pied par code, F3 ou glisser (`AppelBibliotheque.deployerPoste`, `valeursPoste`).
- Module Bibliothèque : calcul des prix et des unités répliqué entre `modules/bibliotheque/js/src/calcul.js` et `CalculElement.cs` (jeu `01_calcul.json`) ; prix d'ouvrage par le moteur de devis (`calculerOuvrage` / `ElementsBibliotheque.CalculerOuvrage`) ; historique des prix par trigger (`ele_maj_par`, `ele_commentaire_prix`) ; coefficients par période répliqués entre `coefficientsEffectifs` (calcul.js) et `CoefficientsElement.cs` (jeu `02_coefficients.json`). Données de démonstration dans `client/src/app/bibliotheque/donnees.js` (puis `npm run generer-vues-liste --workspace client` pour `db/116`).
- Préférences d'affichage dans le `localStorage` du navigateur, jamais en base (raccourcis clavier personnalisés compris).
- Raccourcis clavier personnalisables (`/parametres/raccourcis`) : chaque fonction est déclarée dans un groupe (`declarerRaccourcis` du socle ; grille : `raccourcis.json`, application et page document : `client/src/app/raccourcis.js`) et lue par `actionDe(e, groupe)`, jamais par un test de touche en dur. Clic droit (`ouvrirMenuContextuel`) : menu court, aide-mémoire des raccourcis (grille des lignes, listes) ; tout reste accessible sans lui.
- Module Authentification ([analyse](documentation/conception/ANALYSE-MODULE-AUTHENTIFICATION.md), `modules/authentification/CLAUDE.md`) : session par cookie HttpOnly (`logibtp_session`, jeton haché en base) posée par `/api/auth/connexion` ; `UseAuthentificationSession` (après `UseSocietes`) pose l'utilisateur lu par `Utilisateur.Depuis` ; toute route `/api` exige une session (401 `SESSION_REQUISE`, mot de passe provisoire : 403 `MDP_A_CHANGER`) sauf `/api/sante`, `/api/societe` et les routes publiques de `/api/auth` ; comptes liés à l'individu d'un salarié ou d'un intérimaire (aucun par défaut, pseudo recopié dans `ind_utilisateur`), comptes de service `archivage_ged`, `editions_fond` ; règles des pseudos, mots de passe et états répliquées entre `regles.js` et `ReglesCompte.cs` ; en développement, connexion de test sans mot de passe (`Authentification:ComptesTest`) et mode `EnTetes` ; premier administrateur et secours : `dotnet run --project src/LogiBTP.Api -- comptes creer-admin|reinitialiser|deverrouiller|liste [--societe <code>]`.
- Référentiel des ressources (cœur, `db/195`, `Btp/Ressources.cs`, `client/src/app/ressources/`) : tables `salarie`, `materiel`, `equipe` (plus de `demo_*`), missions d'intérim, habilitations (types paramétrables, fin de validité calculée, état et habilitations manquantes répliqués entre `ressources/regles.js` et `ReglesRessources.cs`, jeux `tests/ressources`), équipes à compositions datées, motifs typés, natures MO → service ; écrans : onglets des fiches salarié et matériel, `/parametres/ressources`, `/ressources/habilitations`.
- Module Calendrier (`modules/calendrier/CLAUDE.md`) : calendriers de travail (plages en minutes, cycle de N semaines depuis une référence, plages datées), jours fériés par règles (DATE, ANNUEL, NIEME, DERNIER, PAQUES, PERIODE ; catalogue français à cocher) et fermetures par portée (société, calendrier, `service:<id>`), temps de travail (`ajouterMinutesTravail`, `minutesTravail`, `prochainTravail`) répliqués entre `calendrier.js` et `ReglesCalendrier.cs` ; calendrier effectif d'une ressource par le cœur (salarié ou matériel, sinon service, sinon défaut : `CalendriersBtp`, `db/196`) ; page `/parametres/calendriers`.
- Module Notifications (`modules/notification/CLAUDE.md`) : boîte par compte (cloche du bandeau relue chaque minute, `/notifications`, préférences `/parametres/notifications`), planificateur de fond par base qui exécute les sources du cœur (`Btp/NotificationsBtp.cs` : rappels du CRM visibles, une notification par couleur ; synthèse quotidienne des habilitations au responsable du service ou aux administrateurs) ; clé de dédoublonnage choisie par la source ; nouvelle source : `AddSourceNotifications<T>()`.
- Module Exécution ([analyse](documentation/conception/ANALYSE-MODULE-EXECUTION.md)), lot 1 : ordres = documents de la famille E (`modules/document/db/019h`, `db/197`) : E_OE (ordre d'exécution lancé depuis la fiche du marché, budget planifié figé à chaque validation, le premier = référence), E_PO, E_DAP ; un chantier par ordre (`EXE_CHANTIER`, `EXE_CHANTIER_UNIQUE`) ; exécution de l'ordre (`ent_exe_*`, service, responsable, dates prévues) modifiable même validé par `/api/execution/documents/{id}` (blocage : motif obligatoire, tâche CRM au service du motif) ; heures MO par `v_heures_lignes` ; liste `ordres` ; module désactivé : ordres hors des listes (`f_module_actif`). Lot 2 (`modules/execution/CLAUDE.md`) : parcours des services par chantier (modèles `/parametres/execution`, `db/198`), état par service répliqué entre `etats.js` et `ReglesEtats.cs` (jeu `01_etats.json`), états imposés, synthèse `/execution/synthese` et vue `/execution/chantier/:id` (`SpecialisationExecutionBtp`).
- Module Pointage ([analyse](documentation/conception/ANALYSE-MODULE-POINTAGE.md), `modules/pointage/CLAUDE.md`), lot 1 : pointages en minutes, toujours sur un chantier (chantiers internes `cha_interne`, `db/199`), type de MO = nature du regroupement MO, sous-types paramétrables (`poi_sous_type`) ; contrôles d'une semaine répliqués entre `controles.js` et `ReglesPointage.cs` (jeu `01_controles.json` : erreurs refusées, avertissements signalés) ; saisie au bureau `/pointage/saisie` (grille hebdomadaire d'un salarié en mode tableau avec saisie en cascade — raccourcis du groupe `pointage` —, couche SAISIE), paramètres `/parametres/pointage`, liste `pointages` ; droit de saisie : le salarié, le responsable de son service (`SpecialisationPointageBtp.PeutSaisirAsync`) ou un administrateur. Lot 2 : synthèse `/pointage/synthese` (salariés à examiner par exceptions, « Tout voir »), couche validée par semaine (`poi_semaine`, la saisie reste intacte), validation simple ou double (RH sans le chef possible), jours validés bloqués, dévalidation avec motif, demandes de correction (tâche CRM au service administratif) ; règles `validation.js` ↔ `ReglesValidation.cs` (jeu `02_validation.json`) ; RH = membre d'un service ADMINISTRATIF, chef = responsable du service (`SpecialisationPointageBtp`). Lot 3 : variables de paie (jamais de calcul de salaire) par profil (`salarie.sal_ppf_id`, `db/200`) : rubriques et règles typées répliquées entre `paie.js` et `ReglesPaie.cs` (jeu `03_paie.json`), saisies des rubriques, zones de déplacement par chantier et agence (`sal_agence`), export CSV des jours validés (`/pointage/export`), valorisation des heures (coût horaire de la fiche, mission d'intérim ou import) et coût réel par chantier (`v_cout_mo_chantier`). Lot 4 : borne d'atelier `/borne` (appareil enregistré, jeton `X-Borne-Jeton` gardé par le navigateur de la borne, route publique `/api/pointage/borne`, aucune session ; PIN haché ; salarié → chantier proposé par le planning du jour ou ordre lu par son numéro → type → heures ; non-conformité avec motif ; saisie d'équipe par le chef, `poi_groupe` modifiable ensemble tant que les pointages sont identiques), administration `/parametres/bornes` (▶ Tester : borne d'essai dans une fenêtre séparée, jeton d'essai de huit heures en mémoire, PIN facultatif, pointages contrôlés puis annulés).
- Module Planning ([analyse](documentation/conception/ANALYSE-MODULE-PLANNING.md), `modules/planning/CLAUDE.md`), lot 1 : composant propre sans métier `VuePlanning` (axe du temps en minutes, échelles heure / demi-journée / jour / semaine, lignes et barres virtualisées, voies des barres superposées, glisser au pas, Ctrl = copie, Alt + clic = scinder, zoom), spécialisé par méthode patron ; prototype `/planning/prototype` (500 ressources, 20 000 tâches). - Transformation et reste à solder ([conception](documentation/conception/CONCEPTION-ACHATS-MARCHES.md), lot 1 réalisé) : tout le reliquat reprend toutes les lignes de prix (soldées à 0, grisées) ; liens recalculés à chaque enregistrement du document cible (`RecalculerLiens`) ; une facture issue d'un BL est aussi liée à la commande (remontée à l'origine) ; colonnes Qté parent / Reste / Soldé (`EditeurDocument.definirRestes`, `GET /documents/{id}/restes`) ; solde écrit à la validation (case `lig_solde` ou seuil : `etatSolde` ↔ `Soldes.Etat`, jeu `modules/document/tests/soldes`), retiré par un avoir ; seuils par famille dans `parametre_document` (`/parametres/documents`). Vues par défaut des documents transformés (une par type, `vues-document.js` → `db/176`) : ventilation sans coefficients (ventes : PV net seul) avec quantité et montant du parent, puis précédent, période et cumul (%, quantité, montant chacun) ; avancement : vue réglée (quantités, % et montants : parent, précédent, cumul), les clés de ventilation y désignant les valeurs d'avancement (`ALIAS_AVANCEMENT`). Documents transformés et d'avancement : ouvrages repliés à l'ouverture et libellés sur une ligne par défaut (préférence `libellesTransformes`). Documents d'avancement : informations du parent non modifiables (seuls l'avancement et le commentaire du document se saisissent, commentaire du parent affiché à part), aucune suppression, ajout de texte ou de lignes de pied seulement (règles de l'interface : `EditeurDocument.champVerrouille`, `ajoutAutorise`). Lot 2 : à la transformation, chaque option ou variante (unité : `unitesOptionnelles` ↔ `Options.Unites`, jeu `modules/document/tests/options`) est retenue (passe en V) ou non (non reprise), la base d'une variante peut être écartée ; refus `OPTION_NON_TRAITEE` ; choix tracés (`document_lien.lie_choix`) ; pour mémoire repris ; source → statut ACCEPTE à l'étape COMMANDE ; une transformation à type intermédiaire (`tra_intermediaire_tyd_id` : devis → facture par une commande) crée et valide ce document (`ent_intermediaire`, `DocumentService.ValiderDans`).
- Adresse des travaux (ventes) ou de livraison (achats) : `ent_adresse_livraison` (instantané { origine CHANTIER|DEPOT|COMPTOIR|LIBRE, libelle, adresse, contact sur place, telephone, instructions, mention }) ; troisième bloc des coordonnées de l'entête (`PanneauxBtp.rendreAdresse`, `structure/adresses.js`) ; reprise du document parent (entête copié), sinon du chantier quand le bloc est vide (contact sur place `cha_contact_ind_id`, `db/184`) ; achats : chantier, dépôt (notre société et ses niveaux inférieurs), retrait au comptoir du fournisseur ou saisie libre (`GET /api/structure/adresses-livraison`) ; avertissement si elle diffère du chantier ; obligatoire à la validation d'une commande fournisseur (`ADRESSE_LIVRAISON`). Ventes : payeur et adresse des travaux identiques au client restent vides (`AdressesDocument.ViderIdentiques` à l'enregistrement et à la validation ↔ `adresseIdentiqueAuClient` / `payeurIdentiqueAuClient`) ; payeur = intervenant PAYEUR seulement (plus de payeur pris d'office égal au client).
