# LogiBTP

- Répondre et documenter en français ; code, commentaires et noms en français (sauf API techniques).
- Architecture : `socle/` (sans métier) → `modules/<nom>/` (classes mères, méthode patron) → cœur (`src/`, `client/`, `db/`) qui spécialise. Un module ne dépend jamais du cœur ; le module Métré ne dépend pas du module Document.
- Moteurs miroirs JS / C# : `MoteurDocument` (`modules/document/js/src/moteur-document.js`, `modules/document/dotnet/LogiBTP.Documents/Calcul/MoteurDocument.cs`) et `MoteurDevisBtp` (`client/src/calcul/moteur-btp.js`, `src/LogiBTP.Calcul/MoteurDevisBtp.cs`). Toute règle modifiée l'est dans les deux, avec un cas dans les jeux du module ou du cœur, puis `npm test`, `npm run exporter-resultats` et `dotnet test LogiBTP.slnx`.
- Jamais de `Number` pour un montant côté JS (decimal.js) ; une seule fonction d'arrondi par moteur (demi vers l'infini).
- Noms de colonnes du DDL partout (snake_case préfixé) ; les propriétés C# en PascalCase s'y mappent automatiquement. Colonnes génériques (`modules/document/js/src/types.js`) et BTP (`client/src/calcul/colonnes-btp.js`) alignées sur les entités (des tests le vérifient).
- Schéma géré par les scripts SQL de chaque module (`modules/*/db`) puis du cœur (`db/`), pas de migrations EF ; les colonnes métier s'ajoutent par `ALTER TABLE` dans le cœur.
- Module Liste : la sémantique des requêtes (recherche, segments, tri, curseur) est répliquée entre `modules/liste/js/src/requete.js` et `ConstructeurRequete.cs` (jeux `modules/liste/tests/cas`) ; toute requête de données s'exécute en lecture seule. Les vues par défaut se modifient dans `client/src/app/vues-liste.js`, puis `npm run generer-vues-liste --workspace client`.
- Module Fiche : validation des champs répliquée entre `modules/fiche/js/src/validation.js` et `ValidationFiche.cs` (jeu `modules/fiche/tests/cas`) ; types de fiches dans `client/src/app/fiches/definitions.js` (puis `npm run generer-vues-liste --workspace client`) ; les règles métier des fiches du cœur existent en JS (`fiches.js`) et en C# (`SpecialisationFicheBtp`). Champs supplémentaires : colonne JSONB par table.
- Module GED : chaîne du coffre-fort répliquée entre `modules/ged/js/src/coffre.js` et `ChaineCoffre.cs` (texte d'entrée, horodatage à la milliseconde UTC, jeu `01_coffre.json`), conservation des versions entre `versions.js` et `RegleVersions.cs` (jeu `02_versions.json`) ; `FournisseurGedMemoire` applique les mêmes règles que `ServiceGed`. Le journal et les documents du coffre sont protégés par des triggers (`db/050`) : ne jamais les contourner.
- Client : application web à routes (`client/src/app/pages`, déclarées dans `pages/index.js`) ; une page dérive de `PageBase` (titre, `modifiee`, `quitter`, `liberer`) et toute ouverture d'écran passe par `app.naviguer(url, { nouvelleFenetre })`, jamais par un panneau superposé. Menus du bandeau et raccourcis : `client/src/app/navigation/menus.js` ; widgets : `navigation/widgets.js`.
- Une base par société (sous-domaine) : les contextes EF prennent la connexion de `SocieteCourante` par requête ; tout cache singleton dépendant du schéma est indexé par base.
- Module Bibliothèque : calcul des prix et des unités répliqué entre `modules/bibliotheque/js/src/calcul.js` et `CalculElement.cs` (jeu `01_calcul.json`, régénérable par un script Node) ; prix d'ouvrage par le moteur de devis (`calculerOuvrage` / `ElementsBibliotheque.CalculerOuvrage`) ; historique des prix par trigger (`ele_maj_par`, `ele_commentaire_prix`). Données de démonstration dans `client/src/app/bibliotheque/donnees.js` (puis `npm run generer-vues-liste --workspace client` pour `db/116`).
- Préférences d'affichage dans le `localStorage` du navigateur, jamais en base.
