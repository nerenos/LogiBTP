# LogiBTP

- Répondre et documenter en français ; code, commentaires et noms en français (sauf API techniques).
- Architecture : `socle/` (sans métier) → `modules/<nom>/` (classes mères, méthode patron) → cœur (`src/`, `client/`, `db/`) qui spécialise. Un module ne dépend jamais du cœur ; le module Métré ne dépend pas du module Document.
- Moteurs miroirs JS / C# : `MoteurDocument` (`modules/document/js/src/moteur-document.js`, `modules/document/dotnet/LogiBTP.Documents/Calcul/MoteurDocument.cs`) et `MoteurDevisBtp` (`client/src/calcul/moteur-btp.js`, `src/LogiBTP.Calcul/MoteurDevisBtp.cs`). Toute règle modifiée l'est dans les deux, avec un cas dans les jeux du module ou du cœur, puis `npm test`, `npm run exporter-resultats` et `dotnet test LogiBTP.slnx`.
- Jamais de `Number` pour un montant côté JS (decimal.js) ; une seule fonction d'arrondi par moteur (demi vers l'infini).
- Noms de colonnes du DDL partout (snake_case préfixé) ; les propriétés C# en PascalCase s'y mappent automatiquement. Colonnes génériques (`modules/document/js/src/types.js`) et BTP (`client/src/calcul/colonnes-btp.js`) alignées sur les entités (des tests le vérifient).
- Schéma géré par les scripts SQL de chaque module (`modules/*/db`) puis du cœur (`db/`), pas de migrations EF ; les colonnes métier s'ajoutent par `ALTER TABLE` dans le cœur.
- Module Liste : la sémantique des requêtes (recherche, segments, tri, curseur, colonnes multivaluées `ARRAY`) est répliquée entre `modules/liste/js/src/requete.js` et `ConstructeurRequete.cs` (jeux `modules/liste/tests/cas`) ; toute requête de données s'exécute en lecture seule. Les vues par défaut se modifient dans `client/src/app/vues-liste.js`, puis `npm run generer-vues-liste --workspace client`.
- Module Fiche : validation des champs répliquée entre `modules/fiche/js/src/validation.js` et `ValidationFiche.cs` (jeu `modules/fiche/tests/cas`) ; types de fiches dans `client/src/app/fiches/definitions.js` (puis `npm run generer-vues-liste --workspace client`) ; les règles métier des fiches du cœur existent en JS (`fiches.js`) et en C# (`SpecialisationFicheBtp`). Champs supplémentaires : colonne JSONB par table. Champs gérés (`gere: true`, sans colonne) : lus et écrits par `SpecialisationFiche.LireGeresAsync / ValiderGeresAsync / EcrireGeresAsync` (mémoire : `types.<type>.geres`).
- Module GED : chaîne du coffre-fort répliquée entre `modules/ged/js/src/coffre.js` et `ChaineCoffre.cs` (texte d'entrée, horodatage à la milliseconde UTC, jeu `01_coffre.json`), conservation des versions entre `versions.js` et `RegleVersions.cs` (jeu `02_versions.json`) ; `FournisseurGedMemoire` applique les mêmes règles que `ServiceGed`. Le journal et les documents du coffre sont protégés par des triggers (`db/050`) : ne jamais les contourner.
- Client : application web à routes (`client/src/app/pages`, déclarées dans `pages/index.js`) ; une page dérive de `PageBase` (titre, `modifiee`, `quitter`, `liberer`) et toute ouverture d'écran passe par `app.naviguer(url, { nouvelleFenetre })`, jamais par un panneau superposé. Menus du bandeau et raccourcis : `client/src/app/navigation/menus.js` ; widgets : `navigation/widgets.js`.
- Une base par société (sous-domaine) : les contextes EF prennent la connexion de `SocieteCourante` par requête ; tout cache singleton dépendant du schéma est indexé par base.
- Module Bibliothèque : calcul des prix et des unités répliqué entre `modules/bibliotheque/js/src/calcul.js` et `CalculElement.cs` (jeu `01_calcul.json`, régénérable par un script Node) ; prix d'ouvrage par le moteur de devis (`calculerOuvrage` / `ElementsBibliotheque.CalculerOuvrage`) ; historique des prix par trigger (`ele_maj_par`, `ele_commentaire_prix`) ; coefficients par période répliqués entre `coefficientsEffectifs` (calcul.js) et `CoefficientsElement.cs` (jeu `02_coefficients.json`). Données de démonstration dans `client/src/app/bibliotheque/donnees.js` (puis `npm run generer-vues-liste --workspace client` pour `db/116`).
- Préférences d'affichage dans le `localStorage` du navigateur, jamais en base.
- Module Annuaire : personnes (niveaux, hiérarchie `per_parent_id`, relations — client, fournisseur… ; « casquettes » dans le code et la base, « relations » à l'écran — qui déverrouillent des groupes de la fiche) et individus, rattachements, liens, coordonnées partagées (`coordonnee` + `usage_coordonnee`, historique par trigger). Contrôles des identifiants (SIREN, SIRET, TVA, IBAN, BIC) répliqués entre `identifiants.js` et `Identifiants.cs` (jeu `01_identifiants.json`) ; plan d'enregistrement des coordonnées (choix MODIFICATION / AUTRE pour une coordonnée partagée modifiée) entre `coordonnees.js` et `PlanCoordonnees.cs` (jeu `02_coordonnees.json`) ; `FournisseurAnnuaireMemoire` applique les mêmes règles que `ServiceAnnuaire`. Données de démonstration dans `client/src/app/annuaire/donnees.js` (puis `npm run generer-vues-liste --workspace client` pour `db/141`).
- Module Entreprises françaises : correspondance d'un résultat de l'API Recherche d'entreprises répliquée entre `correspondance.js` et `Correspondance.cs` (jeu `01_correspondance.json`, entreprise fictive) ; le serveur relaie l'API, la démo hors ligne l'interroge depuis le navigateur.
- Salariés et annuaire : chaque salarié est lié à un individu (`demo_salarie.sal_ind_id`), rattaché à l'agence de notre société ; à l'enregistrement d'un salarié, l'individu reprend identité, rôle et rattachement (`SalariesAnnuaire.cs` / `synchroniserSalarie` dans `client/src/app/annuaire/salaries.js`). Données : `db/142_annuaire_salaries.sql` et `annuaireDesSalaries` (démo hors ligne). Les vues de l'annuaire sont ensemblistes (`DISTINCT ON`) : pas de fonction par ligne (volumes de salariés).
- Graphe relationnel de l'annuaire : parcours (hiérarchie, liens, rattachements, profondeur 1 à 5, niveaux supérieurs toujours présents, contacts résumés au-delà d'un maximum) répliqué entre `construireGraphe` (`modules/annuaire/js/src/graphe.js`) et `GrapheAnnuaire.cs` (jeu `03_graphe.json`) ; disposition en couches (`disposerGraphe`, contacts en colonnes) et vue `VueGraphe` côté client ; page `/annuaire/graphe?type=&id=&profondeur=` et onglet Graphe des fiches.
- Rattachements (contacts) : lus par page (`pageRattachements` / `ServiceAnnuaire.PageRattachements`, 20 par page avec recherche ; la fiche lit la première page et `nb_rattachements`) ; le champ géré `rattachements` n'enregistre que les rattachements modifiés, ajoutés ou retirés (`supprime: true`) — un rattachement absent de la saisie est inchangé.
- Pied des documents en tranches : structure `pied` du résultat (totaux calculés TOTAL_HT, HT_NET, TOTAL_TTC, SOUS_TOTAL, NET ; groupes HT, TVA, TTC ; sous-totaux de pied ; un total égal au suivant est `masque`) et bases de calcul (CUMUL, TOTAL_HT, HT_NET, TOTAL_TTC, LIGNE = sous-total de pied `lig_pied_base_id` ; mode C coefficient) répliquées entre les deux `MoteurDocument` (jeu `06_pied_tranches_bases.json`). L'éditeur affiche ces lignes calculées comme lignes virtuelles (`_virtuelle`, identifiants ≤ −10¹²), jamais saisissables.
- Affichage de la saisie (`modules/document/db/013`) : étiquettes de lignes globales (`etiquette_ligne`) complétées ou personnalisées par document (`ent_etiquettes`), couleur du mode de vente (`couleur_type_prix`) en seconde couleur de la pastille, modèles de saisie (`ent_modele`) et vues de colonnes (`vue_document` : globales ou par utilisateur, une par défaut par type et modèle, mode débogage avec colonnes système). Vues par défaut du cœur dans `client/src/app/vues-document.js` (puis `npm run generer-vues-liste --workspace client` pour `db/150`) ; la vue choisie est mémorisée dans le navigateur par type et modèle.
- Page document : panneaux ancrables (`.dock[data-dock-id]` : détail, plan) répartis par `Disposition` dans trois zones (gauche, droite, bas) ; positions, tailles et visibilité dans le navigateur. Plan du document (`PlanDocument`) : tranches (titres) et pied ; « Aller à » ou « Filtrer » (filtre d'affichage seulement : `EditeurDocument.filtrer`, la saisie et le calcul portent sur tout le document). Le pied entier est une tranche virtuelle repliable (`ID_PIED`). Lots du devis de démonstration générés par `client/src/app/demo-lots.js`.
- Type de ligne SECTION (11) : tranche racine non numérotée englobant le corps (le pied reste à la racine), totalisée comme un titre (`estTranche` / `TL.EstTranche`), erreur `SECTION_RACINE` hors racine (jeu `modules/document/tests/cas/07_section.json`). Ne pas comparer les identifiants de type numériquement (`estPied`, `estTypeNumerote`, `accepteEnfants`).
- Coefficient de prorata (`lig_coef_prorata`, 1 par défaut) : porté par les seules lignes vendues (lignes de prix, jamais les composantes d'ouvrage, remises à 1 par `ReglesBtp.appliquerContexte`), appliqué au PV affiché après les frais annexes, avant la remise (jeu `tests/cas/14_prorata_lignes_vendues.json`) ; exclu du calcul du coefficient de frais annexes (un PV affiché imposé en est d'abord retiré) ; répliqué entre `moteur-btp.js` et `MoteurDevisBtp.cs` (jeu `tests/cas/13_coef_prorata.json`). Onglet Analyse (`client/src/app/analyse-coefs.js`) : ventilation des coefficients par nature et total de la portée choisie dans l'arbre des tranches (document entier, section, titres) ; aide à la saisie qui écrit sur les lignes.
- Onglet Analyse : calculs dans `client/src/app/analyse-calcul.js` (feuilles, agrégats, éléments regroupés par code et libellé (`elementsAnalyse`, `modificationsElement` : PR écrit par le FG, PV en prix fixe ; `repartirQuantite` : quantité totale (perte et ouvrages parents compris) reventilée au prorata, quantités saisies recalculées, métrés désactivés mais conservés), marges brute = prix client − déboursé et nette = PV remisé sans FA ni prorata − revient, `forcerMontant`), interface dans `analyse-coefs.js`. Les montants sont les vraies valeurs : un montant saisi recalcule les coefficients des feuilles, les plus fortes absorbent l'arrondi, et en dernier recours une ligne d'écart d'arrondi est ajoutée dans la nature (test `client/test/analyse-calcul.test.js`, vérifié après recalcul par le moteur).
- Recherche dans les lignes (`RechercheLignes`, Ctrl+F ou 🔍 dans la page document) : sans filtre, lignes trouvées surlignées (`EditeurDocument.marquer`), passage de résultat en résultat avec dépliage des tranches (`allerA(id, { focus })`). Codes du devis de démonstration : `coderDemo` (`OUV-nnn`, éléments par nature, même libellé = même code).
- Glisser-déposer bibliothèque → document (entre fenêtres, HTML5) : la liste de la bibliothèque rend ses lignes glissables (option `glisser` de `ListeDonnees`, types `application/x-logibtp-article|ouvrage`, données `{ id, code, bib, type, societe }`) ; la grille accepte le dépôt (`actions.depotExterne`) avec un badge indiquant l'intégration (avant / après au même niveau, comme composante, dans la tranche), puis `AppelBibliotheque.deposer` insère l'élément (`insererContenu(..., { position })`). Raccourcis de la grille dans `socle/js/src/ui/raccourcis.json` (Ctrl+flèches : ordre et niveau).
- Bibliothèque : type ENSEMBLE (structure réutilisable) : composition enracinée sur une tranche (titre) portant des paramètres `$` (`variables-tranche.js`, aussi dans le détail d'un titre de devis) lus par les métrés et libellés de ses lignes (vendues, options, variantes) ; prix = totaux de la tranche (`calculerEnsemble` / `ElementsBibliotheque.CalculerEnsemble`, jeu `tests/cas/15_ensemble_tranche_parametree.json`). Liste des éléments : sélection multiple (Ctrl / Maj), glisser de plusieurs éléments (`AppelBibliotheque.deposer` les insère en une étape).
- Document → bibliothèque (`client/src/app/bibliotheque/envoi.js`, bouton « 📤 Vers la bibliothèque ») : élément → article, ouvrage → ouvrage, titre / section → ensemble ; lien par l'ID (`lig_art_id`, `lig_proprietes.element.id`) pour la mise à jour ; sinon doublons par code (même bibliothèque) ou libellé proposés au rattachement, ou création (code et bibliothèque au choix). Écritures par les fiches `element` (verrou, empreinte) ; composition extraite du sous-arbre (quantités absolues rendues relatives, `compositionDepuisContenu`) ; coefficients de la ligne imposés à l'élément.
- Structure des affaires (`db/160_structure.sql`, démo `db/161` générée depuis `client/src/app/structure/donnees.js`) : projets (chiffrage), affaires (regroupement de chantiers ou gestion `G`), chantiers (ouverts quand un projet passe « Obtenu » : la fiche projet le propose), marchés (proposés à la validation d'une commande client : création ou rattachement, `structure/marche-commande.js`). Documents rattachés par `ent_projet_id`, `ent_affaire_id`, `ent_chantier_id`, `ent_marche_id` (section Rattachement de l'entête ; un marché complète son chantier, un chantier son affaire : `completerRattachement` / `PUT /api/structure/documents/{id}/rattachement`, permis sur un document validé). Fiches dans `fiches/fiche-structure.js` (codes `PRJ-AAAA-NNN`, `M-<chantier>-<rang>`), listes `v_liste_projets|affaires|chantiers|marches` (facturé = factures + factures d'avancement − avoirs validés) et `FournisseurStructureMemoire` hors ligne. Type `V_SITUATION` (état cumulé non comptable, transformé en facture d'avancement du delta). Traçabilité des quantités (phase 2) à venir.
- Intervenants (petit annuaire, `db/162_intervenants.sql`, démo `db/163` générée) : fonctions `fonction_intervenant` (portée S structure / D document / T tous, unique, paiement direct ; répliquées dans `FONCTIONS_INTERVENANT`, test de parité) ; structure : table `intervenant` (un objet par ligne), champ géré `intervenants` des fiches (`Intervenants.cs` ↔ `FournisseurStructureMemoire.geres`), contrôles répliqués entre `Intervenants.Controler` et `controlerIntervenants` ; documents : instantané `ent_intervenants` (JSONB de l'entête, enregistré avec le document, copié à la transformation), tiers du document = première ligne (client ou fournisseur, synchronise `ent_tiers_id`, facultatif en brouillon, obligatoire à la validation `TIERS_OBLIGATOIRE`), reprise du marché / chantier / projet. Interface commune `structure/intervenants.js` (contacts = rattachements du tiers, coordonnées du rattachement). Vue `v_intervenants` (structure et documents) pour les courriels à venir.
- Page document : rattachement saisi par code (double-clic ou F4 : `structure/selection.js`), libellé en lien vers la fiche, parents complétés par l'enfant (marché → chantier → affaire et projet) ; variables du document ($$, sans ligne ni métré, évaluées en premier par les moteurs) éditées dans le métré de la ligne SECTION (`variablesDocumentSur` de l'hôte du panneau métré) ; section sans code : numéro du document dans la colonne Code ; actions de la bibliothèque (prix, envoi) dans le détail de la ligne ; onglet Pièces = GED du document (`type_element` = code du type, `id_element` = groupe des indices), pièces jointes à envoyer (`dge_a_envoyer`, option `envoi` de `ExplorateurGed`, module Mail à venir). Paiement direct des intervenants : information seulement (montants et agréments : gestion de la sous-traitance à venir).
