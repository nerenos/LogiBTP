- Dépendances externes par module (npm, NuGet, polices) : [DEPENDANCES.md](documentation/DEPENDANCES.md), généré par `npm run rapport-dependances` à relancer après tout ajout ou mise à jour.

- Répondre et documenter en français ; code, commentaires et noms en français (sauf API techniques).
- Architecture : `socle/` (sans métier) → `modules/<nom>/` (classes mères, méthode patron) → cœur (`src/`, `client/`, `db/`) qui spécialise. Un module ne dépend jamais du cœur ; le module Métré ne dépend pas du module Document.
- Moteurs miroirs JS / C# : `MoteurDocument` (`modules/document/js/src/moteur-document.js`, `modules/document/dotnet/LogiBTP.Documents/Calcul/MoteurDocument.cs`) et `MoteurDevisBtp` (`client/src/calcul/moteur-btp.js`, `src/LogiBTP.Calcul/MoteurDevisBtp.cs`). Toute règle modifiée l'est dans les deux, avec un cas dans les jeux du module ou du cœur, puis `npm test`, `npm run exporter-resultats` et `dotnet test LogiBTP.slnx`.
- Jamais de `Number` pour un montant côté JS (decimal.js) ; une seule fonction d'arrondi par moteur (demi vers l'infini).
- Codes (statuts, natures, états, erreurs testées par l'interface) : jamais en dur ; `js/src/codes.js` de chaque module (objets `Object.freeze`) ↔ `Codes.cs` (constantes), parité vérifiée par le `CodesTests` du module (`Constantes.Ecarts` de `LogiBTP.Socle.Testing`) ; communs aux modules dans le socle (`NIVEAU_NOTIFICATION`, `PROFIL`, `ACTION_DROIT`, `NIVEAU_CONFIDENTIALITE`, `VariablesEnv` ; refus du paramétrage : `u.ExigerAdmin()`) ; cœur : `client/src/app/codes.js` ↔ `src/LogiBTP.Domaine/Codes.cs` (`TYPE_FICHE`, `TYPE_DOCUMENT`, `MODULE_FACULTATIF`… ; adresses par `urlFiche` / `urlDocument`) ; seul le SQL des requêtes garde ses littéraux.
- Noms de colonnes du DDL partout (snake_case préfixé) ; les propriétés C# en PascalCase s'y mappent automatiquement. Colonnes génériques (`modules/document/js/src/types.js`) et BTP (`client/src/calcul/colonnes-btp.js`) alignées sur les entités (des tests le vérifient).
- Schéma géré par les scripts SQL de chaque module (`modules/*/db`) puis du cœur (`db/`), pas de migrations EF ; les colonnes métier s'ajoutent par `ALTER TABLE` dans le cœur.
- Module Liste : la sémantique des requêtes (recherche, segments, tri, curseur, colonnes multivaluées `ARRAY`) est répliquée entre `modules/liste/js/src/requete.js` et `ConstructeurRequete.cs` (jeux `modules/liste/tests/cas`) ; toute requête de données s'exécute en lecture seule. Les vues par défaut se modifient dans `client/src/app/vues-liste.js`, puis `npm run generer-vues-liste --workspace client`.
- Module Fiche : validation des champs répliquée entre `modules/fiche/js/src/validation.js` et `ValidationFiche.cs` (jeu `modules/fiche/tests/cas` ; `erreurRequete` ↔ `ErreurRequete` pour les listes par requête SQL) ; paramétrage : RGPD des champs du logiciel (`pcf_confidentiel`), champs supplémentaires par onglet / groupe / ordre, liste de valeurs par SELECT (lecture seule, côté serveur), type mot de passe chiffré (`POST /{id}/secret`, journalisé) ; types de fiches dans `client/src/app/fiches/definitions.js` (puis `npm run generer-vues-liste --workspace client`) ; les règles métier des fiches du cœur existent en JS (`fiches.js`) et en C# (`SpecialisationFicheBtp`). Champs supplémentaires : colonne JSONB par table. Champs gérés (`gere: true`, sans colonne) : lus et écrits par `SpecialisationFiche.LireGeresAsync / ValiderGeresAsync / EcrireGeresAsync` (mémoire : `types.<type>.geres`). Code à chrono (`definition.chrono` des types, `modules/fiche/js/src/chrono.js` ↔ `ChronoFiche.cs`, jeu `02_chrono.json`) : code prévisionnel en italique à la création (le compteur n'avance qu'à l'enregistrement d'un code calculé, rang pris sauté), code saisi contrôlé en direct, déjà pris → prochain code libre proposé (`CODE_PRIS`) ; code modifié après la création : droit `MODIFIER_CODE` ; formats dans `/parametres/referentiels` (Codes des fiches) ; marché : `{PARENT}` = code du chantier (`CodeParentChronoAsync`), suffixe saisissable ; élément : compteur par bibliothèque ; créations hors fiche par `IChronosFiches` du socle (tiers provisoire, projet du CRM ; trigger T + identifiant en secours, `modules/annuaire/db/072`).
- Module GED : chaîne du coffre-fort répliquée entre `modules/ged/js/src/coffre.js` et `ChaineCoffre.cs` (texte d'entrée, horodatage à la milliseconde UTC, jeu `01_coffre.json`), conservation des versions entre `versions.js` et `RegleVersions.cs` (jeu `02_versions.json`) ; `FournisseurGedMemoire` applique les mêmes règles que `ServiceGed`. Explorateur : arborescence du cœur `ArborescenceBtp` (`client/src/app/ged/arborescence.js` : Projet › Affaire › Chantier › Marché › famille (Ventes, Achats, Stock) › type de document › documents, dossiers virtuels pour la famille et le type ; liens symboliques vers les documents enfants dans un regroupement, enfants imbriqués depuis un document) ; un dépôt dans un dossier lie la pièce à l'élément du dossier.
