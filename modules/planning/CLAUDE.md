# Module Planning – contexte

## Rôle
- Planification des tâches des chantiers et des services sur des ressources ([analyse](../../documentation/conception/ANALYSE-MODULE-PLANNING.md)). Lot 1 : composant d'affichage propre, sans métier (axe du temps, lignes, barres, glisser, virtualisation), spécialisé par méthode patron. Lot 2 : tâches théoriques (sans affectation, charge du service) et fonctionnelles, affectations, calcul par les plages des ressources (modes 1, 2, 3), vues fournies, à planifier.
- Ne connaît ni les chantiers, ni les ressources, ni les calendriers : ressources, plages travaillées, équipes, chantiers et budgets fournis par la spécialisation (`SpecialisationPlanningBtp`).

## Dépendances
- JS `@logibtp/planning` → `@logibtp/socle` (`echapper`). .NET : `LogiBTP.Planning` (règles), `LogiBTP.Planning.Web` → `LogiBTP.Socle.Web`, EF Core Npgsql. Jamais du cœur ni d'un autre module (le Calendrier est lu par le cœur).
- Utilisé par : cœur (`client/src/app/pages/planning.js` : page `/planning?vue=&du=` ; `planning-prototype.js` ; `Btp/SpecialisationPlanningBtp.cs` ; `db/201`).

## Structure
- `js/src/temps.js` : instants « AAAA-MM-JJTHH:MM » ↔ minutes depuis 1970 (`versMinutes`, `depuisMinutes`, `dateDe` ; calcul en UTC, sans changement d'heure), `ECHELLES` (HEURE, DEMI_JOUR, JOUR, SEMAINE : minutes par colonne, groupe d'en-tête), `debutUnite` (JOUR, SEMAINE = lundi, MOIS), `semaineIso`, `colonnes` (libellés, week-ends), `groupes` (jours, semaines, mois), `arrondirAuPas`, `periodeFlottante`.
- `js/src/disposition.js` : `empiler` (voies des barres qui se chevauchent, glouton par début), `cumuler` (positions des lignes), `ligneA` (dichotomie), `visibles` (barres d'une ligne triée qui coupent un intervalle, avec la durée maximale).
- `js/ui/vue-planning.js` : `VuePlanning` (coin, en-tête du temps, en-têtes des lignes et corps défilant synchronisés ; dessin des seules lignes et barres visibles avec une marge, à l'image suivante ou par minuterie de repli, `actualiser()` immédiat ; fond par dégradé répété et bandes de week-end ; hauteur fixe ou adaptée aux voies ; glisser : déplacer — changement de ligne sauf `ligneFixe` —, bords = agrandir, au pas ; Ctrl = copie, Alt + clic = scinder ; sélection, double-clic, menu, dépôt HTML5 ; `definirDonnees`, `majTache`, `ajouterTache`, `supprimerTache`, `regler`, `zoomer`, `allerA` ; méthode patron `contenuBarre`, `classeBarre`, `titreBarre`, `enteteLigne`, `classeLigne`). `js/ui/planning.css` (variables `--vp-entete`, `--vp-voie`, `--vp-couleur`).

- `js/src/calcul.js` ↔ `dotnet/LogiBTP.Planning/ReglesPlanning.cs` (jeu `tests/cas/01_calcul.json`) : `calculerTache` (contributeurs = ressources à capacité, plages moins absences ; sans ressource à capacité : calendrier par défaut × `nb_ressources` ; segments à rythme constant ; mode 1 : fin à la minute supérieure, heures par ressource ; mode 2 : heures entre début et fin ; mode 3 : ventilation par jour au prorata du temps travaillable, reste au dernier jour, idem par ressource ; erreurs PLA_CALENDRIER, PLA_FIN, PLA_HEURES), `retirerAbsences`, `MESSAGES_CALCUL`. C# : `Temps` (minutes depuis 1970 ↔ instants, dates).
- `db/089_planning.sql` (rejouable) : `pla_tache` (mode de calcul, début / fin `timestamp(0)`, heures en minutes, nombre de ressources, service, élément, origine, parent, libellé, mémo, avancement, couleur, état OPTION / PREVUE / CONFIRMEE / EN_COURS / TERMINEE, mobile, habilitations, version), `pla_affectation` (type et identifiant de la ressource, équipe d'origine, heures, quantité), `pla_vue` (définition JSONB : regroupement RESSOURCE / CHANTIER / SERVICE, échelle, avant / après, services, types, hauteur adaptée ; vues fournies ATELIER_JOUR, POSE_SEMAINE, CHANTIERS_GANTT, CHARGE_SERVICE, LIVRAISONS).
- `dotnet/LogiBTP.Planning.Web/ServicePlanning.cs` : entités, `PlanningDbContext`, `SpecialisationPlanning` (`RessourcesAsync`, `PlagesAsync`, `PlagesServiceAsync`, `EquipesAsync`, `MembresAsync`, `ElementsAsync`, `BudgetsAsync`, `ServicesAsync`), `ServicePlanning` (vues, données d'une période : vue ressources = lignes groupées par service, une barre par affectation, tâches théoriques sur la ligne du service ; vue chantiers ou services = une barre par tâche ; calcul côté serveur : équipe développée en membres à la date de début, plages sur 120 jours en mode 1, absences = affectations des tâches `absence` ; création, modification et suppression avec verrou optimiste `tac_version` (409 `PLA_VERSION`), déplacement — mode 1 : fin recalculée ; 2 et 3 : durée gardée —, redimensionnement — heures recalculées, mode gardé —, réaffectation de → vers, copie, scission ; à planifier = budget − heures des tâches de l'élément et du service). `Extensions.cs` (`AddModulePlanning<T>`, `MapModulePlanning`).

## Routes HTTP (préfixe `/api/planning`, module activé par société)
- `GET|PUT /vues`, `GET /referentiels`, `GET /donnees?vue=&du=&au=&recherche=`, `GET /ressources?services=&types=&recherche=`, `GET /elements?recherche=`, `GET /a-planifier?services=&recherche=`, `POST /calcul`, `GET|PUT|DELETE /taches/{id}`, `POST /taches`, `POST /taches/{id}/deplacer` { debut, fin, mode, de, vers, copie, version }, `POST /taches/{id}/scinder` { instant, version }.

## Tests
- `npm test --workspace modules/planning/js` (axe du temps, disposition, calcul) ; `dotnet test modules/planning/dotnet/LogiBTP.Planning.Tests` (même jeu de calcul). Prototype : `/planning/prototype?ressources=500&taches=20000` (mesures affichées : génération, données, dessin).
