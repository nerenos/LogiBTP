# Module Exécution – contexte

## Rôle
- Suivi de l'exécution par élément (chantier) ([analyse](../../documentation/conception/ANALYSE-MODULE-EXECUTION.md) § 3, 4) : parcours des services (modèles, étapes amont), état de chaque service calculé d'après le parcours et les ordres, états imposés à la main, synthèse et vue détaillée.
- Les ordres eux-mêmes sont des documents de la famille E (module Document, spécialisés par le cœur : `Btp/ExecutionBtp.cs`) ; ce module ne les lit que par sa spécialisation. Ne connaît ni les chantiers, ni les services, ni les documents.

## Dépendances
- JS `@logibtp/execution` : aucune. .NET : `LogiBTP.Execution` (règles), `LogiBTP.Execution.Web` → `LogiBTP.Socle.Web`, EF Core Npgsql. Jamais du cœur ni d'un autre module.
- Utilisé par : cœur (`SpecialisationExecutionBtp` : services de `db/193`, chantiers suivis, ordres de la famille E ; `db/198` : services et modèles de démonstration ; pages `client/src/app/pages/execution.js`).

## Structure
- `js/src/etats.js` ↔ `dotnet/LogiBTP.Execution/ReglesEtats.cs` (jeu `tests/cas/01_etats.json`) : `ETATS_SERVICE` (SANS_OBJET, A_VENIR, EN_ATTENTE, EN_COURS, BLOQUE, TERMINE), `etatOrdre` (annulé / remplacé ignoré ; bloqué ; soldé ou terminé ; en cours ; brouillon = à faire ; en attente ; transmis sans état = en cours), `etatsServices` (étapes du parcours + ordres + états imposés : un service sans ordre est « à venir » tant qu'une étape amont n'est pas terminée, « en attente » ensuite ; un état imposé l'emporte, `ecart` s'il diffère de l'automatique ; services hors parcours mais avec ordres inclus), `controlerParcours` (PAR_CODE, PAR_DOUBLON, PAR_SERVICE, PAR_AMONT, PAR_BOUCLE), `MESSAGES_EXECUTION`.
- `js/src/etapes.js` ↔ `dotnet/LogiBTP.Execution/ReglesEtapes.cs` (jeu `tests/cas/02_etapes.json`) : étapes d'un ordre (états personnalisés de son type) : `predecesseurs` (amonts, sinon l'étape précédente), `etapesAValider` (étapes masquées — sans date obligatoire — validées d'office avec la suivante, `ETP_ORDRE`, contrôle du N+1 bloquant `ETP_CONTROLE` ou alerte `ETP_CONTROLE_ATTENTE`), `controlerAnnulation`, `etapeEnCours`, `etatExecution` (bloqué reste bloqué ; rien de validé : à faire ; tout : terminé ; étape en cours d'attente : en attente), `datesPrevues` (enchaînement par bornes de jours : H sur les minutes du calendrier, OUV jours à minutes > 0, CAL ; jalon = durée nulle ; validée = date de validation, imposée gardée), `controlerEtapes`, `NATURES_ETAPE`, `UNITES_ETAPE`, `MESSAGES_ETAPES`.
- `js/ui/atelier.js` (+ `atelier.css`, export `@logibtp/execution/ui`) : `EcranEtapesAtelier` (écran tactile des étapes : ordres et étapes fournis, étape proposée = en cours, « ✓ … terminé », recherche par numéro ; fournisseur `{ charger, valider, ordre }` ; aucun contrôle du N+1), page tablette et borne du cœur.
- `db/085_execution.sql` (rejouable) : `exe_parcours_modele`, `exe_parcours_etape` (`pae_amonts` TEXT[] de codes), `exe_parcours` (un par élément : `par_type_element`, `par_id_element`, modèle d'origine), `exe_parcours_element_etape` (copie modifiable des étapes), `exe_etat_manuel` (élément, service, état, motif, auteur, date).
- `db/085b_execution_etapes.sql` (rejouable) : `exe_etat_catalogue` (global : nature TACHE / JALON / ATTENTE, durée, unité H / OUV / CAL, couleur, service), `exe_etat_type` (états d'un type d'ordre : ordre, date obligatoire, contrôle du N+1 et bloquant, statut documentaire déclenché ENVOYE / VALIDE, amonts, durée propre), `pae_etats` / `pee_etats` (états retenus par une étape de parcours, JSON `[{ code, duree }]`, vide = ceux du type), `exe_ordre_etape` (étapes d'un ordre : copie modifiable, dates prévisionnelles, imposée, validation, contrôle, ressource JSON, tâche du planning).
- `dotnet/LogiBTP.Execution.Web/ServiceEtapes.cs` : entités, `ServiceEtapes` (catalogue, états d'un type, `AppliquerTypeAsync` — E41 —, `AtelierAsync` (étapes pour l'atelier), `ActionAsync(…, droitVerifie)` (droit vérifié par l'application : borne), étapes d'un ordre copiées de son étape de parcours, sinon de son type, à la première lecture — `InitialiserAsync` —, actions VALIDER / ANNULER (motif) / CONTROLER / DECONTROLER / PREVOIR / RESSOURCE / DUREE, `RecalculerToutAsync`) ; planning ↔ étapes : à la lecture, une tâche liée (`ore_tac_id`) impose son dernier jour et sa ressource à l'étape non validée (`SynchroniserPlanningAsync`), une action transmet les tâches à déplacer, à terminer et les contrôles attendus (`SuitesEtapes.Deplacements|Terminees|AControler`) ; `LierTacheAsync`, `EtapesOrdreAsync` ; points d'accroche de `SpecialisationExecution` : `OrdreAsync`, `TachesAsync`, `OrdresEnCoursAsync`, `CalendrierAsync`, `PeutValiderAsync`, `PeutControlerAsync`, `ApresEtapesAsync` (`SuitesEtapes` : état déduit, statuts atteints, dates, historique).
- `dotnet/LogiBTP.Execution.Web/ServiceExecution.cs` : entités, `ExecutionDbContext`, DTO, `SpecialisationExecution` (`TypeElement`, `ServicesAsync`, `ElementsAsync(filtre, ids)`, `OrdresAsync(ids)`, `TypesInactifsAsync` : étapes d'un type d'ordre désactivé ignorées, leurs avals héritent de leurs amonts — `Actives`), `ServiceExecution` (`ModelesAsync`, `EnregistrerModelesAsync` — administrateur, contrôle des étapes —, `EnregistrerParcoursAsync` — modèle copié ou étapes saisies, vide = parcours retiré —, `EnregistrerEtatManuelAsync` — état vide = retour à l'automatique —, `SyntheseAsync` — filtre recherche, service, état —, `DetailAsync`) ; un ordre sans service prend celui de l'étape de même type d'ordre. `Extensions.cs` (`AddModuleExecution<T>`, `MapModuleExecution`).

## Routes HTTP (préfixe `/api/execution`, module activé par société)
- Étapes : `GET|PUT /etats` (catalogue), `GET|PUT /etats-types/{type}`, `POST /etats-types/{type}/appliquer`, `GET /ordres/{id}/etapes` ({ etapes, en_cours, etat, peut_valider, peut_controler, avertissements }), `PUT /ordres/{id}/etapes/{code}` { action, date, ressource, commentaire, duree }, `POST /ordres/{id}/etapes/recalculer`.
- `GET|PUT /parcours-modeles` ; `GET /synthese?recherche=&service=&etat=` ; `GET /elements/{type}/{id}` ; `PUT /elements/{type}/{id}/parcours` { pam_id?, etapes? } ; `PUT /elements/{type}/{id}/services/{srv}/etat` { etat, motif }.

## Textes et icônes (module Personnalisation, lot P3m)
- Textes `execution.*` du `fr.json` du module (`etapes` : natures, unités, erreurs ; `etats` : états des services, erreurs du parcours ; `atelier` : écran tactile), icônes `execution_*` (natures, états), couleurs de l'écran tactile `--exe-*` (`js/personnalisation/theme.css`) ; `NATURES_ETAPE` et `ETATS_SERVICE` gardent leur forme { libelle, icone } par accesseurs ; tests avec le dictionnaire (`test/preparation.js`). Écrans du cœur : `execution_btp.*`, icônes `execution_btp_*`, couleurs `--execution-*` de `client/personnalisation/theme.css`.
