# Module Sous-traitance – contexte

## Rôle
- Pièces exigées des sous-traitants et des marchés de sous-traitance ([analyse](../../documentation/conception/ANALYSE-MODULE-SOUS-TRAITANCE.md) § 5.3, ST12, ST13, ST18) : liste paramétrable, ajustements par élément (pièce ajoutée ou dispensée, motif), conformité d'un marché ou d'un sous-traitant, pièces bloquantes par action (commande, facture, paiement).
- Les documents (appels d'offres, commandes, factures : famille T du module Document) et les marchés (table `marche` de sens ST) sont tenus par le cœur ; ce module ne les connaît que par sa spécialisation. Les pièces fournies sont des documents de la GED lus par le cœur.

## Dépendances
- JS `@logibtp/sous-traitance` : `@logibtp/socle` (décimaux). .NET : `LogiBTP.SousTraitance` (règles), `LogiBTP.SousTraitance.Web` → `LogiBTP.Socle.Web`, EF Core Npgsql. Jamais du cœur ni d'un autre module.
- Utilisé par : cœur (`Btp/SousTraitanceBtp.cs` : `SpecialisationSousTraitanceBtp` ; contrôles de validation des documents T par `ControlerPiecesAsync` ; courriel « st_pieces » du module Mail ; source de notifications `SourcePiecesSousTraitance`), client (`client/src/app/sous-traitance/pieces.js`, `pages/parametres-sous-traitance.js`).

## Structure
- `js/src/conformite.js` ↔ `dotnet/LogiBTP.SousTraitance/ReglesConformite.cs` (jeu `tests/cas/01_conformite.json`) : `applicable` (conditions : marché public, garantie, montant minimal), `finValidite` (saisie, sinon dépôt + durée), `etatPiece` (FOURNIE, A_ECHEANCE dans le délai de rappel, EXPIREE, MANQUANTE, ABSENTE si facultative, DISPENSEE), `conformite` (pièces applicables ou ajustées, la plus récente de sa catégorie, conforme = aucune obligatoire manquante ou expirée, `a_echeance`, `bloquants` par action), `ajouterMois`, `ETATS_PIECE`, `ACTIONS_BLOQUEES`, `PORTEES_PIECE`.
- `js/src/ventilation.js` ↔ `dotnet/LogiBTP.SousTraitance/ReglesVentilation.cs` (jeu `tests/cas/02_ventilation.json`) : `ventilerFactureRecue` (facture reçue répartie au prorata du reste de chaque ligne, cumul saisi → période, période négative au prorata du précédent, arrondi demi vers l'infini absorbé par la ligne de plus forte base ; `VENT_DEPASSEMENT`, `VENT_SANS_RESTE`, `VENT_SANS_LIGNE`), `MESSAGES_VENTILATION` ; dépend de `@logibtp/socle` (décimaux).
- `js/src/paiement-direct.js` ↔ `dotnet/LogiBTP.SousTraitance/ReglesPaiementDirect.cs` (jeu `tests/cas/03_plafonds.json`) : `montantPaiementDirect` (TTC, HT en autoliquidation), `delaiAcceptation` (réception + 15 jours, alerte à J-3), `controlerAcceptation` (montant ≤ demande, cumul ≤ montant agréé, refus total ou partiel motivé ; état ACCEPTEE / PARTIELLE / REFUSEE ; `PD_*`), `ETATS_PAIEMENT_DIRECT`, `MESSAGES_PAIEMENT_DIRECT`.
- `js/src/retenue.js` ↔ `dotnet/LogiBTP.SousTraitance/ReglesRetenue.cs` (jeu `tests/cas/04_retenue.json`) : `liberationRetenue` (réception + 1 an, 29 février → 28 février ; réserves non levées : bloquée ; levées après l'échéance : libération à la levée ; `RET_RECEPTION`, `RET_RESERVES`), `MESSAGES_RETENUE`.
- `db/092_sous_traitance.sql` (rejouable) : `stt_piece_type` (code, libellé, portée TIERS / MARCHE, catégorie GED, obligatoire, durée en mois, rappel en jours, `spt_bloquant` TEXT[], conditions, modèle d'édition, ordre, actif ; pièces fournies par défaut une fois), `stt_piece_element` (ajustements : élément `marche` ou `personne`, mode AJOUTEE / DISPENSEE, motif).
- `db/092b_sous_traitance_paiement_direct.sql` (rejouable) : `stt_paiement_direct` (une demande par facture : mode DIRECT / DELEGATION, facture au client, montants demandé et accepté, état RECUE → ACCEPTEE / PARTIELLE / REFUSEE → TRANSMISE → PAYEE, dates, motif).
- `dotnet/LogiBTP.SousTraitance.Web/ServicePaiementDirect.cs` : `ServicePaiementDirect` (`SuiviAsync` : factures du marché, demandes, cumuls accepté / payé, reste agréé, factures au client proposées ; `DeclarerAsync` : facture validée, montant proposé ; `AccepterAsync` : `ReglesPaiementDirect.Controler` sur le cumul des autres demandes ; `TransmettreAsync` : paiement direct = facture au client hors validée, puis `LierAsync` ; `PayerAsync` ; `SupprimerAsync` avant transmission ; `AEcheanceAsync` pour les rappels) ; mode selon la garantie du marché (PAIEMENT_DIRECT → DIRECT, DELEGATION → DELEGATION sans déduction ni plafond).
- `dotnet/LogiBTP.SousTraitance.Web/ServiceSousTraitance.cs` : entités, `SousTraitanceDbContext`, `SpecialisationSousTraitance` (`MarcheAsync` — avec montant agréé et autoliquidation —, `PiecesAsync(tiers, marche)`, `DefinirValiditeAsync`, `FactureAsync`, `FacturesAsync`, `FacturesClientsAsync`, `LierAsync`, `ApresDemandeAsync`), `ServiceSousTraitance` (`TypesAsync`, `EnregistrerTypesAsync` — administrateur —, `ConformiteMarcheAsync`, `ConformiteTiersAsync`, `BloquantsAsync(marche, action)`, `AjusterAsync` — motif obligatoire pour dispenser —), `Extensions` (`AddModuleSousTraitance<T>`, `MapModuleSousTraitance`).

## Routes HTTP (préfixe `/api/sous-traitance`, module activé par société)
- `GET /marches/{id}/paiements` ; `POST /factures/{id}/paiement` { recue_le, facture_client_id, montant } ; `POST /paiements/{id}/accepter` { montant, motif, le } ; `POST /paiements/{id}/transmettre` { le, facture_client_id } ; `POST /paiements/{id}/payer` { le } ; `DELETE /paiements/{id}`.
- `GET|PUT /pieces-types` ; `GET /marches/{id}/conformite` ; `GET /tiers/{id}/conformite` ; `PUT /elements/{marche|personne}/{id}/pieces/{code}` { mode, motif } ; `PUT /pieces/{dge}/validite` { valide_au }.

## Textes et icônes (module Personnalisation, lot P3n)
- Textes `sous_traitance.*` du `fr.json` du module (`pieces` : états, actions bloquées, portées ; `paiement_direct` : états, erreurs ; `retenue`, `ventilation` : erreurs), icônes `sous_traitance_piece_*` et `sous_traitance_pd_*` ; `ETATS_PIECE` et `ETATS_PAIEMENT_DIRECT` gardent leur forme { libelle, icone } par accesseurs, les autres tables par `textesParCode` ; tests avec le dictionnaire (`test/preparation.js`). Écrans du cœur : `sous_traitance_btp.*`, icônes `sous_traitance_btp_*`, couleurs `--sous-traitance-*` de `client/personnalisation/theme.css`.
