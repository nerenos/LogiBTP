# Module Facturation électronique – contexte

- Plan par lots : [facturation-electronique.md](../../documentation/conception/plans/facturation-electronique.md) ; analyse : [ANALYSE-FACTURATION-ELECTRONIQUE.md](../../documentation/conception/ANALYSE-FACTURATION-ELECTRONIQUE.md) ; décisions : [facturation-electronique-questions.md](../../documentation/conception/plans/facturation-electronique-questions.md).

## Rôle
- Réforme RFE : codes des normes, modèle sémantique EN16931, cycle de vie des factures (lot 1) ; lecture CII / Factur-X / UBL, schematrons, CDAR (lot 5), connecteur de plateforme, file et journal (lots 2 à 9) ; écriture et e-reporting (partie B).
- Sans métier : ne connaît ni les pièces, ni les tiers ; le cœur les fournira par spécialisation (lot 11). Ne dépend ni de Document, ni d'Édition, ni d'OAuth.

## Dépendances
- JS `@logibtp/facture-electronique` → `@logibtp/socle` (decimal, dictionnaire, composants d'interface) ; `vite` en développement (page de démonstration, lot 9) ; développement seulement (outil et tests, lot 4) : `saxon-js` et `xslt3` 2.7.0 (licence Saxonica, gratuite, redistribution binaire sans modification permise ; pas open source), `xmllint-wasm` 5.3.0 (MIT, libxml2 en WebAssembly). .NET : `LogiBTP.FactureElectronique` → `LogiBTP.Socle`, PdfPig 0.1.16 (Apache-2.0, fichiers embarqués des PDF) ; `LogiBTP.FactureElectronique.Web` (lot 6) → module, `LogiBTP.Socle.Web`, `Microsoft.AspNetCore.App`, EF Core Npgsql 10.0.3 (lot 8). Jeton par `IFournisseurJeton` du socle, jamais par le module OAuth. Jamais du cœur ni d'un autre module.

## Repères (lot 1)
- Codes `js/src/codes.js` ↔ `dotnet/LogiBTP.FactureElectronique/Codes.cs` (parité par `CodesTests`) : valeurs des normes, clés en français. `TYPE_FACTURE` (BT-3, BR-FR-04), `CADRE_FACTURATION` (BT-23, BR-FR-08, B1 à M9), `CATEGORIE_TVA`, `TRAITEMENT` (note BAR), `CODE_NOTE`, `SOUS_TYPE_LIGNE`, `STATUT_CDV` (+ listes `STATUTS_TERMINAUX`, `STATUTS_MOTIF_OBLIGATOIRE` (BR-FR-CDV-15 : 206, 207, 208, 210, 213, 501), `STATUTS_OBLIGATOIRES_PPF` ↔ `StatutCdv.Terminaux`…), `EMETTEUR_STATUT`, `SENS_FACTURE` (E / R), `MOTIF_STATUT` (51 codes BR-FR-CDV-CL-09), `ACTION_CDV` ; API XP Z12-013 : `SYNTAXE`, `PROFIL_FACTURE` (pas `PROFIL`, pris par le socle), `TYPE_FLUX`, `SENS_FLUX` (In / Out), `REGLE_TRAITEMENT`, `ETAT_ACCUSE`, `NIVEAU_ACCUSE`, `MOTIF_ACCUSE` ; file et journal : `ETAT_FLUX`, `EVENEMENT_FE` ; `ERREUR_FE`.
- `js/src/cycle-vie.js` ↔ `ReglesCycleVie.cs` (jeu `tests/cas/01_cycle_vie.json`, motifs générés depuis l'onglet « Tableau des motifs de STATUTS » de l'annexe A XP Z12-012 V1.4) : `emetteurDuSens` (E → VENDEUR, R → ACHETEUR), `emetteursStatut` (onglet « Acteurs CDV »), `motifsAutorises` (Rejetée selon PA_E / PA_R, Refusée B2B ou B2G), `statutTerminal`, `motifObligatoire`, `obligatoirePpf`, `controlerStatut` / `Controler` (liste d'`ERREUR_FE`), `statutsPosables`, `statutAffiche`.
- Enchaînement contrôlé seulement pour un statut posé par la société (émetteur = rôle du sens) : rien après Rejetée / Refusée, facture émise : rien avant Déposée, Déposée une fois, Complétée en réponse à Suspendue. Un statut reçu n'est contrôlé que sur code, émetteur, motif et action.
- Statut affiché : premier terminal, sinon le plus avancé (rang interne, à égalité le plus récent).
- `ModeleFacture.cs` (C# seul) : `Facture` (BG-0) et ses groupes (parties, payeur EXT-FR-FE-BG-02, agents, livraison, période, totaux, TVA, pièces jointes, lignes avec ligne parente, sous-type et facture antérieure EXT-FR-FE-BG-06). Montants en `decimal`.

## Repères (lot 2 : lecture, C# seul)
- `Formats/LectureCii.cs` : XML CII D22B (CII seul ou XML d'un Factur-X) → `Facture` ; chemins de l'annexe A (onglets « CII D22B & FX EN16931 FR » / « EXT-CTC-FR »). Ordre : `Charger` (sans DTD ni résolution externe), racine `rsm:CrossIndustryInvoice`, `Profil` (BT-24 ↔ `SpecificationFacture` : BASIC WL et BASIC → `Basic`, EN16931 → `CIUS`, EXTENDED Factur-X / ZUGFeRD / CTC-FR → `Extended-CTC-FR` ; MINIMUM refusé), XSD, termes. BT-17 / BT-18 / BT-122 distingués par `TypeDocumentReference` ; SIREN, TVA (VA), fiscal (FC) par `SchemaIdentifiant`. Lignes de groupe ou d'information sans quantité ni prix : lues à 0, unité vide. `Facture.Specification` garde le BT-24 lu.
- `Formats/ValidationXsd.cs` : `JeuXsd` (CII D22B uncoupled ; Factur-X 1.09.2 BASIC WL, EN16931, EXTENDED) ; XSD embarqués (ressources `xsd/<dossier>/<fichier>` depuis `artefacts/xsd`, `schemaLocation` résolus dans l'assemblage seulement), compilés une fois. CII seul → D22B ; XML Factur-X → XSD Factur-X du profil (BASIC sur celui d'EN16931).
- `Formats/ExtractionFacturX.cs` : `factur-x.xml` (à défaut noms ZUGFeRD) de l'arbre `/EmbeddedFiles` par PdfPig, puis `LectureCii` en mode Factur-X.
- Erreurs : `ExceptionLectureFacture` (`Code` d'`ERREUR_FE` : `XML_ILLISIBLE`, `SYNTAXE_INCONNUE`, `XSD_INVALIDE` avec les messages en `Details`, `PROFIL_INCONNU`, `DONNEE_INVALIDE`, `PDF_ILLISIBLE`, `XML_ABSENT`).
- Artefacts : `artefacts/` (XSD, `VERSION`, `LICENCE` Apache-2.0 du paquet FNFE 1.4.0.04) ; exemples : `tests/exemples/` (CII EN16931 et EXTENDED-CTC-FR, Factur-X BASIC WL / EXTENDED, trois PDF, `VERSION`), `tests/exemples/logibtp/` (cas construits : S5 avec payeur, agent, projet, pièce jointe, facture antérieure en ligne). Mise à jour : recopier les dossiers du paquet sans modification et mettre à jour les `VERSION`.

## Repères (lot 3 : lecture UBL, C# seul)
- `Formats/LectureUbl.cs` : UBL 2.1 `Invoice` ou `CreditNote` → même `Facture` que le CII (onglets « Flux 2 UBL EN16931 FR » / « EXT-CTC-FR ») ; conventions du CII : BT-8 UNTDID 2005 → 2475 (`CODE_EXIGIBILITE_TVA_UBL` → `CODE_EXIGIBILITE_TVA`), BT-21 du préfixe `#CODE#` de la note ; raison sociale = `RegistrationName`, à défaut `PartyName` ; sous-ligne = `BillingReference` de ligne avec `DocumentStatusCode`, autre `BillingReference` de ligne = facture antérieure ; CreditNote : BT-9 `PaymentMeans/PaymentDueDate`, BT-11 `AdditionalDocumentReference` type 50 ; rabais nul ignoré ; BT-90 (`SEPA`) hors identifiants. Profils : EN16931, CIUS `#compliant#`, EXTENDED-CTC-FR.
- `Formats/Lecture.cs` : point d'entrée (`Detecter`, `Lire` → `FactureLue(Syntaxe, Facture)`) : PDF (« %PDF- » dans le premier Ko) → Factur-X, sinon racine XML → CII ou UBL, sinon `SYNTAXE_INCONNUE`. `Formats/OutilsLecture.cs` : outils communs (chargement sans DTD, décimaux, termes obligatoires).
- XSD `artefacts/xsd/ubl-2.1/` (`JeuXsd.UblInvoice`, `UblCreditNote`) ; XSD embarqués lus avec DTD interne permise (xmldsig), références externes refusées.
- Égalité CII ↔ UBL : `LectureUblTests` compare le modèle sérialisé en JSON de chaque paire (13 cas FNFE `tests/exemples/{cii,ubl}/`, jumeaux `logibtp/*_CII.xml` / `*_UBL.xml`) ; tout nouveau cas dans les deux syntaxes s'y ajoute en jumeaux.
- Contact CII : BT-41 = `PersonName` seul (`DepartmentName` BT-41-0 non lu).

## Repères (lot 4 : schematrons, outil Node seulement)
- Pas de validation XSLT 2.0 dans le serveur (Q6) : `js/outils/valider.js` (`validerFacture(chemin | contenu, { warning, facturX })`, `controlesAEnchainer`, `extraireXmlFacturX`) sert aux tests et à l'administration : `npm run valider-facture -- <fichier>… [--warning] [--facturx] [--json]` (racine ou workspace ; code de sortie 1 si une erreur fatale).
- Enchaînement (note explicative FNFE 1.4.0) : `ETAPE_CONTROLE.XSD` (xmllint-wasm, mêmes XSD que `JeuXsd`) → `PROFIL` (EN16931 CII / UBL, EXTENDED-CTC-FR CII / UBL, ou Factur-X BASIC WL / EN16931 / EXTENDED) → `FRANCE` (BR-FR-Flux2 CII / UBL, standard « fatal » ou `--warning` ; CDAR : XSD CDAR D22B puis BR-FR-CDV). Une erreur XSD arrête l'enchaînement. Factur-X : PDF (XML extrait des flux FlateDecode), option `facturX`, ou BT-24 propre à Factur-X (BASIC WL, BASIC, EXTENDED Factur-X / ZUGFeRD) ; écart avec le C# : un XML seul BASIC WL ou EXTENDED Factur-X passe par le XSD Factur-X, pas D22B. EXTENDED-CTC-FR → schematron EXTENDED-CTC-FR-CII même en Factur-X.
- Rapport SVRL → `{ etape, niveau (NIVEAU_CONTROLE : flag du SVRL, absent = fatal), regle (@id), message, emplacement (chemin allégé) }` ; `valide` = aucun fatal.
- SEF non versionnés (5 Mo chacun, 61 Mo en tout) : `npm run compiler-schematrons [-- --forcer]` (`js/outils/schematrons.js`) les produit dans `js/.sef/` (ignoré par git, une minute sur 4 cœurs), recompilés d'eux-mêmes quand le XSLT change (empreinte SHA-256 + chemin, `empreintes.json`) ; le test les compile s'ils manquent. Sans `-relocate` : le SEF garde l'URI du XSLT pour les `document('…_codedb.xml')`.
- **Mise à jour des artefacts** (nouveau paquet FNFE) : 1. recopier sans modification les `1xsd` dans `artefacts/xsd/` et les `2xslt` dans `artefacts/schematrons/` (même rangement ; BR-FR-Flux2 en une copie, vérifier qu'elle est identique dans tous les dossiers du paquet par `md5sum`) ; 2. mettre à jour `artefacts/VERSION` (paquet, commit, versions et licences) et `tests/exemples/VERSION` (exemples recopiés de `Z.example/TEST`) ; 3. un fichier renommé : `SCHEMATRONS` / `JEUX_XSD` (`js/outils/schematrons.js`) et `JeuXsd` (`ValidationXsd.cs`) ; 4. `npm run compiler-schematrons`, `npm run valider-facture -- $(find modules/facture-electronique/tests/exemples -name '*.xml' -o -name '*.pdf')` (aucune erreur fatale ; un cas LogiBTP refusé se corrige dans `tests/exemples/logibtp/`), `npm test --workspace @logibtp/facture-electronique`, `dotnet test`.
