# Client LogiBTP (cœur, application web Vite)

## Rôle
- Application web du cœur (`logibtp-client`, workspace npm) : spécialise les paquets JS des modules (`@logibtp/socle`, `metre`, `document`, `liste`, `fiche`, `ged`, `navigation`, `bibliotheque`, `graphe`, `annuaire`, `entreprises-fr`, `import`) ; aucun module ne dépend du client.
- En ligne : API C# par `/api` (proxy Vite vers `http://localhost:5080`, ou `LOGIBTP_API` pour une autre instance ; `Host` conservé pour choisir la société). L'application exige l'API (plus de démo hors ligne) : injoignable au démarrage (`api.disponible()` sur `/api/sante`), écran « Serveur injoignable » recontrôlé toutes les 15 s puis rechargement (`Application.#attendreApi`) ; fournisseurs des modules toujours ceux de l'API (`services()`).
- Application installable et hors ligne (PWA, lot 2) : `public/manifest.webmanifest`, `public/icone.svg` ; service worker `src/pwa/sw.js` complété à la construction par le plugin de `vite.config.js` (règles `src/pwa/regles.js` sans les `export`, testées par `test/pwa.test.js`, fichiers de l'application, version) → `dist/sw.js` ; enregistré par `src/pwa/enregistrement.js` dans le client construit seulement (`npm run apercu --workspace client` : construction + aperçu sur 4173 avec le proxy de l'API, configuration `client-pwa` de `.claude/launch.json`). Fichiers de l'application gardés (cache d'abord), navigation → `index.html` gardé ; lectures de l'API (GET et POST de lecture `LECTURES_POST`) réseau d'abord puis réponse gardée (cache `logibtp-donnees`, en-tête `X-LogiBTP-Hors-Ligne` = date de mise en cache) ; panne = erreur réseau, 502 à 504 ou 500 sans JSON ; écriture ou lecture jamais consultée hors ligne → 503 `HORS_LIGNE` ; données effacées à la déconnexion (`purgerDonnees`) et au changement de compte (`signalerCompte`). Démarrage sans API avec le service worker et une session gardée : application hors ligne (`#passerHorsLigne` : bandeau « ● Hors ligne », classe `hors-ligne` du corps, contrôle toutes les 15 s).
- Saisie des documents hors ligne (lot 3, `src/app/hors-ligne/`) : file IndexedDB `logibtp-hors-ligne` par compte et par document (`attente.js` : `ecrireAttente`, `lireAttente`, `listeAttente`, `marquerAttente`, `retirerAttente` ; entrée = dernier envoi calculé, saisie de l'éditeur, version de départ `depart` pour la fusion, création à faire ; états ATTENTE / CONFLIT / ERREUR ; rien n'est effacé à la déconnexion) ; page document : serveur injoignable (`app.apiPerdue` ou erreur `estHorsLigne`) → enregistré sur le poste (`#enregistrerSurPoste`, bandeau `.document-attente`), rouvert depuis la file (`chargerDocument`), création hors ligne à identifiant provisoire négatif (`#nouveauHorsLigne`, `/document/-<n>`, définitions de tous les types préchargées une fois par session : `prechargerDefinitions`), verrou repris au retour (`verrouAReprendre`), verrou d'un autre sans activité depuis deux minutes : « poste hors ligne ou fenêtre fermée » ; envoi (`synchro.js` : `envoyerAttentes` au démarrage, au retour de l'API et après reconnexion, une fenêtre à la fois par `navigator.locks` ; `envoyerDocument` depuis la page ; création `api.creer` puis entête fusionné `enteteACreer` — défauts du serveur, champs saisis hors ligne —, puis enregistrement ; 409 → CONFLIT, autre refus → ERREUR) ; sujet `hors-ligne-envoye` : la page reprend numéro et identifiants (`documents/reponse.js` `appliquerReponse`, commun avec l'enregistrement direct) ; pastille ⏳ du bandeau (`SUJET_ATTENTE`, lien vers le document le plus ancien ou en erreur). Tests : `test/hors-ligne.test.js`.
- Fusion à trois voies (lot 4) : `hors-ligne/fusion.js` (`fusionner({ depart, local, serveur }, { choix, mode })` → { saisie, conflits, changements } : par entité — entête, lignes, métrés, variables, ventilations — puis par champ, champs calculés jamais en conflit (recalculés par le moteur), compléments d'une ligne suivant son sort, parents restaurés, ordre renuméroté, entités gardées mais supprimées sur le serveur ré-identifiées en négatif (`reidentifier`) ; `mode: 'ecraser'` ; `copieLocale` ; tests `test/fusion.test.js`) ; page `/fusion/document/:id` (`pages/fusion-document.js` : conflits champ par champ — départ, ma saisie, serveur —, modifications prises d'office, ✓ Fusionner et vérifier, ⇥ Garder ma saisie (FORCER ou administrateur), ⧉ Copie en brouillon (seul choix si le document a été validé), ✕ Abandonner ma saisie) ; saisie fusionnée = entrée FUSION (base `depart` = version actuelle du serveur) rouverte dans la page document, envoyée quand l'utilisateur enregistre ; liens « ⇄ Comparer et fusionner » du bandeau du document et de la pastille ⏳ (`urlAttente`).

## Structure
- `src/main.js` : CSS des modules puis `new Application().demarrer()` (`window.__logibtp` en développement).
- Politique de sécurité du contenu (module Droits, D32, option C) : `CSP` de `vite.config.js` (scripts du domaine seulement, styles en ligne permis) en `Content-Security-Policy-Report-Only` sur le serveur de développement et l'aperçu ; en production, l'API (`ClientWeb` du socle, image Docker) pose la même politique en mode bloquant ; aucun script en ligne : `public/demarrage-theme.js` (thème avant l'affichage) et `public/demarrage-apercu.js` (aperçu de la page quittée) ; jamais d'`eval` ni de `new Function`.
- `src/app/application.js` : `Application` (routeur, fenêtres et session du module Navigation, bandeau, `naviguer(url, { nouvelleFenetre })`, `ouvrirElement`, `fermerPage` : fermeture d'une fiche ou d'un document — bouton ✕ Fermer de la page document —, fenêtre séparée fermée) ; `services()` crée une fois les fournisseurs `{ liste, fiche, ged, bibliotheque, annuaire, entreprises, structure }` (API ou mémoire) ; `LISTE_PAR_TYPE` (liste de retour d'une fiche).
- `src/app/api.js` : `api` (documents, verrous, transformation, traçabilité/origine, `/structure/*`, étiquettes, couleurs, vues de document, `auth` : session, politique, connexion, connexion de test, déconnexion, mot de passe) ; cookie de session envoyé par le navigateur (plus d'en-tête d'utilisateur) ; `ErreurApi`.
- Session (module Authentification) : `app.session` (`GET /api/auth/session` au démarrage) ; sans session en ligne, seule `/connexion?retour=` s'ouvre (`pages/connexion.js` : identifiant, mot de passe, Rester connecté, comptes de test en développement) ; mot de passe provisoire : `/compte?changer=1` (`pages/compte.js` : Mon compte, changement par `controlerMotDePasse` de `@logibtp/authentification`, déconnexion) ; `fetch` surveillé : 401 `SESSION_REQUISE` → connexion (dans une autre fenêtre si la page a des modifications), 403 `MDP_A_CHANGER` → Mon compte ; `app.deconnecter()` ; sujet `session` diffusé aux autres fenêtres ; gestion des comptes (administrateur) : `comptes/comptes.js` (`rendreComptePersonne` : compte d'une personne ou création avec pseudo proposé, profil, validité, mot de passe provisoire affiché une fois ; `pastilleCompte`, `profilsComptes`), page `/parametres/comptes` (`pages/parametres-comptes.js` : liste par état, nouveau compte par recherche de la personne, `?compte=<id>` : compte et journal), onglet Compte de la fiche salarié (option `compte` de `FicheSalarie`, posée par `pages/fiche.js`) ; `utilisateur()` / `profil()` = la session.

## Frais annexes (règles, décisions : [CONCEPTION-VENTILATION-FRAIS.md](../documentation/conception/CONCEPTION-VENTILATION-FRAIS.md))
- Portée : une tranche F dans une section (jamais hors section : `FA_HORS_SECTION`, rien n'est ventilé) ; pas de frais de pied ; une ligne seule n'est jamais une unité de frais. Plusieurs portées se cumulent.
- Répartition : sans clé, au prorata du montant hors frais ; clés partielles (total < 100 %) = reste au prorata, avec un bouton « Répartir le reste » pour l'imposer ; au-delà de 100 % : erreur non bloquante. Les écarts ne bloquent jamais la validation.
- Clé en montant : par unité de quantité pour une ligne (la part totale suit la quantité) ; pour un élément ou une nature, en total. Clé d'élément = code et libellé saisi sans balises. Un élément ou une nature visé dans un ouvrage reporte sa part sur l'ouvrage au prorata des montants de ses feuilles.
- PV affiché fixe « avec frais annexes » : exclu de la ventilation, garde son PV, coefficient 1 ; une clé qui le vise est ignorée et signalée (ne plus absorber les frais). PV fixe « avant frais annexes et remise » : reçoit des frais.
- Options et variantes : lignes selon `ent_fa_lignes` (V / OA / OAM) ; mode de calcul `ent_fa_mode` (C / B) ; décision par défaut : une option reçoit le coefficient des lignes vendues de sa portée sans réduire leur part (le choix a/b sur le document est décidé, à vérifier dans le code) ; lignes pour mémoire : jamais de frais.
- Arrondis : la part de chaque ligne est mesurée après arrondi du PV ; les clés en % d'une tranche s'arrondissent ensemble (100 % = le prévu exact) ; le reste en écart `FA_ECART`.
- Cycle : copie et nouvel indice reprennent les clés (documents autonomes) ; copier-coller et duplication de lignes : clés recréées sur les copies comme si elles avaient été saisies (`PressePapiersBtp` : clé de ligne vers la tranche copiée, ou la même tranche dans le même document ; clés d'élément et de nature d'une tranche copiée) ; les clés orphelines sont signalées dans le rapport et supprimées à la validation seulement ; la transformation conserve les tranches F et le détail ; validation et transformation figent la ventilation en clés de ligne (`FigerVentilation`). Historique des clés dans l'instantané du document ; écran de restauration : à faire (TACHES).
- Bibliothèque : les frais ventilés ne vont jamais dans un élément ; l'envoi d'un élément envoie ses PA, les coefficients FG et bénéfice sont ceux par défaut de la base ; une tranche F insérée dans un document devient une unité de frais sans clé.
- Tranche F : jamais éditée (pas de numéro, montant en italique, hors total) ; ne pas comparer `lig_tyl_id` numériquement (`estFraisAnnexes`).

## Conventions et pièges
- Montants en decimal.js (`D`, `S`, `arrondir` du socle), jamais `Number` ; toute règle de `moteur-btp.js` se reporte dans `src/LogiBTP.Calcul/MoteurDevisBtp.cs` avec un cas dans `tests/cas`.
- Colonnes de `colonnes-btp.js` alignées sur `DocumentBtp` / `DocumentLigneBtp` (test xUnit `Colonnes_btp_alignees_avec_le_moteur_js`).
- Répliques C# : `controlesValidation` ↔ `SpecialisationBtp.ControlerValidation` ; `controlerIntervenants` ↔ `Intervenants.Controler` ; `synchroniserSalarie` ↔ `SalariesAnnuaire.Synchroniser` ; `completerRattachement` ↔ `PUT /api/structure/documents/{id}/rattachement` ; règles de `fiches.js` / `fiche-annuaire.js` ↔ `SpecialisationFicheBtp`.
- `vues-liste.js`, `fiches/definitions.js`, `vues-document.js`, `bibliotheque/donnees.js`, `annuaire/donnees.js`, `structure/donnees.js` : source unique du SQL généré → après modification, `npm run generer-vues-liste --workspace client`.
- Ouverture d'écran : `app.naviguer(url, { nouvelleFenetre })`, jamais de panneau superposé. Questions et saisies courtes : `confirmer` / `alerter` / `saisir` du socle (`<dialog>`), jamais `confirm` / `alert` / `prompt`. Listes de choix : combos saisissables (`ListeDeroulante`), jamais de `<select>` simple. Préférences dans le `localStorage`.
